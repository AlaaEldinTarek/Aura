## 3. Reusable pattern (from the post-check card)
`PostCheckCard` is the model: one object per notification family with `show(...)` (build + post), `cardLayoutId(dark, arabic)` (4 layouts), `isDark(context)` (app `theme_mode` via `FlutterPrefs`, `PostCheckActions.isDark` rule: dark/amoled -> dark, light -> light, system -> phone), `isArabic(context)` (prefs `language` in `aura_prayer_times`), icon helper, and `refreshShowing(context)` (called from the `updatePrayerWidgets` handler in `MainActivity.kt`, which Dart already calls on theme and language change).
Proposed shared helper `ThemedNotification` (Kotlin, new file): `isDark`, `isArabic`, `pickLayout(dark, arabic, light, dark, lightRtl, darkRtl)`, `iconBitmap(prayerName)` (move of `PostCheckCard.iconBitmap` + `PostCheckActions.iconKey`), and a small registry `refreshAll(context)` that each phase adds one entry to. Live refresh keeps: same id, `setOnlyAlertOnce(true)`, original `when`, remaining timeout.
Raw data for a rebuild (prayer name, count, title, body) is stored in the notification's own `extras` (no prefs key), as the post-check card does.

Limits that apply to every phase:
- **Theme** can always be re-applied live. **Language** can be re-applied live only when the text is built in Kotlin from structured data (post-check, daily summary, azkar, Jumu'ah, azan-stopped). Task, wird and digest text arrives from Dart already translated at schedule time; after a language change it only follows when Dart reschedules (whether it does: UNKNOWN, check before that phase).
- **Lock screen**: the working pattern on this EMUI phone is ongoing + PRIORITY_MAX + VISIBILITY_PUBLIC + a plain LinearLayout. P1 of the post-check work showed a NON-ongoing HIGH/PUBLIC notification is hidden on the lock screen before face match. Whether dismissible themed reminders show there is UNKNOWN until each is checked with the phone ALREADY LOCKED when it fires (see section 8: the P1 test fired while unlocked, so it did not prove they are hidden). They stay dismissible; only if one is hidden does it become ongoing with a timeout.
- **Buttons**: system `addAction` shows max 3 and EMUI does not color them; themed buttons need custom RemoteViews (as the post-check card).
- Only 2 notification IDs/channels exist per family already; **no notification ID changes** anywhere. Channels: reuse the existing channel unless a phase says otherwise (importance cannot be raised later; a new channel is a contract change: Kotlin + Dart if Dart references it + `.project-docs/contracts/notification-ids.md` in one commit).

## Phase TC (Draft, owner idea 2026-11-20): live countdown timers in notifications

### TC.1 Mechanism: RemoteViews Chronometer
- `<Chronometer>` is a RemoteViews-allowed view; `setChronometer(id, base, format, started)` and `setChronometerCountDown(id, true)` (API 24, minSdk 24) tick in the system UI process. **VERIFIED in this app**: the Aura widgets already use `setChronometer` with `android:countDown="true"` (`PrayerWidgets.kt:221,305`, `combined_prayer_widget*.xml`), so the view class and call work in our RemoteViews. **UNKNOWN**: inside a notification card on this EMUI (collapsed, expanded, lock screen, the public version). Needs a device check in the first TC step.
- `base` is in the `SystemClock.elapsedRealtime()` timebase: `base = elapsedRealtime() + (targetEpochMs - nowEpochMs)`. Store the absolute target epoch in the notification extras (like title/body today), never the base, and recompute the base on every (re)post. Then a live theme/language refresh (`ThemedNotification.refreshAll` re-post, same id, original `when`) keeps the timer correct and seamless: the new RemoteViews gets a base for the same absolute moment.
- Format string: `setChronometer(id, base, "Due in %s", true)` puts the words and the timer in one view (one `%s`). Shows `mm:ss`, and `h:mm:ss` from one hour.
- **Battery: VERIFIED by design, not measured.** The ticking is a Handler inside the system UI process, running only while the notification view is on screen (shade open, lock screen with the screen on); it stops when the view is hidden or the screen is off. The app gets no wakeups and runs no service for it. The only extra wakeups are the explicit alarms listed below.

### TC.2 Where, text, and what happens at zero
**Zero:** in count-down mode the Chronometer does not stop at 0, it keeps going and shows a minus (`-00:01`), so every timer needs a switch at its target time.

1. **Task card (makes sense, best fit).** Only for the "before" reminder (task has a due time and the reminder fires X minutes before): the card shows the countdown to the due time. Kinds "due now", "today" (09:00, no due time) and "pending" (after Remind Later) have nothing to count down, so they keep the plain body.
   - English "Due in 04:32" / Arabic "موعد المهمة بعد 04:32" (digits: see TC.3).
   - **At the due time: one new exact alarm** (`setExactAndAllowWhileIdle`, same style as the existing task alarm), armed when the card is posted, cancelled by Done, Remind Later and by `TaskReminderReceiver.cancel`. It re-posts the same notification id with the body "Task is due now" / "حان موعد المهمة الآن", `setOnlyAlertOnce(true)`, original `when`, no new sound. Not the existing alarm (that one fires at the reminder time, before the due time) and not `setTimeoutAfter` (that would remove the task card at zero).
   - New contract items: intent action `com.aura.hala.TASK_DUE_NOW`, PendingIntent request code **id+4** (family id, +1 tap, +2 snooze, +3 done; the action differs, so it cannot collide with the original alarm that uses the plain id), new `scheduleNativeTaskReminder` arg `dueAt` (epoch ms, Dart already knows it) and intent extra `due_at`; update `method-channels.md`, `intent-extras.md` in the same commit as Dart and Kotlin. No new notification id, no new channel, no prefs key.
   - Layouts: one extra `Chronometer` (id `task_reminder_countdown`) next to the body TextView in all 4 task layouts, visibility toggled (body TextView for non-countdown kinds). Remind Later after the due time re-arms as today.
2. **Post-check card (weak fit).** The card is the "did you pray?" question and is removed after 30 minutes (`PostCheckActions.TIMEOUT_MS`). The next prayer is always more than 30 minutes away (shortest gap is Fajr to Sunrise), so the zero case never happens while the card shows, and no switch or alarm is needed. But the next-prayer countdown is up to hours (`h:mm:ss`) and does not help answering the question. Options: (a) skip it, (b) a small line "Next: Asr in 2:14:05" / "العصر بعد ..." under the buttons (more height on the card), (c) count down the 30 minutes left to answer. Recommendation: (a) skip unless the owner wants (b). No contract change for any option (no alarm, no new key).
3. **Jumu'ah reminder (fits, but after T7).** The reminder fires 30 minutes before Zuhr on Friday, so a countdown to Zuhr runs 30:00 to 0. English "Jumu'ah in 12:30" / Arabic "الجمعة بعد 12:30". At zero: no alarm and no re-post needed, `setTimeoutAfter(zuhrMs - now)` removes the card at Zuhr (the azan takes over). It is a plain system notification today, not a themed card, so it should come with T7 (themed Jumu'ah card), not before. Needs today's Zuhr time from `aura_prayer_times` `dhuhr_time` at fire time (already read in `schedule`); unknown Zuhr = no countdown. No contract change.

### TC.3 Arabic digits
- **UNKNOWN on the screen, expected NOT Arabic.** `Chronometer` formats with `DateUtils.formatElapsedTime`, which uses the phone's default locale, not the app language. This phone's locale is `en-EG` (read with `getprop persist.sys.locale`), so in the Arabic app the timer would show Latin digits (`29:59`) next to Arabic text. Not verified visually (no probe build).
- Fallbacks, simplest first: (a) accept Latin digits in the timer only (the layout already forces `textDirection="ltr"`, monospace like the widgets), documented as a known limit; (b) bundle a font whose digit glyphs 0-9 are drawn as Arabic-Indic digits and set it on the Chronometer in the Arabic layouts only (RemoteViews inflates with the app's resources, so `res/font` is expected to work, **UNKNOWN until tried**); (c) no live timer in Arabic, static minutes text refreshed by alarms every minute (extra wakeups, the thing we want to avoid; not recommended). Recommendation: first TC step shows what the device really does, then choose (a) or (b).
